2.1. 100% DYNAMIC 24/7 ENGINE & REAL BAR INGESTION
--------------------------------------------------
Requirement:
The system must run 24/7, continuously monitoring prices and calculating signals
dynamically without static hardcoded tables or stale numbers.

Implementation & Architecture:
- SSE Real-Time Heartbeat: The server maintains an event stream broadcasting
  refreshed market snapshots and model updates every 4 seconds.
- Real Bar Ingestion (api/_lib/bar-cache.js): Replaced hardcoded sine-wave price
  generators with live daily and 15-minute OHLCV bar ingestion from Yahoo Finance
  (NSE equity symbols, e.g., RELIANCE.NS, TCS.NS, INFY.NS).
- Resilient Disk Caching: Fetched bar history is cached in `.private/cache/`
  with a 15-minute TTL, ensuring reliable offline fallback, network resilience,
  and fast sub-millisecond query performance during volatile sessions.
- Data Provenance Contract: Every symbol emits clear data provenance flags:
  `hasObservedPrice: true`, `priceSource: "NSE_YAHOO_BARS"`, and
  `historicalBarsAreSynthetic: false`.

2.2. SIGNAL AGE, DURATION, AND VOLATILITY-BASED DYNAMIC DAYS
-----------------------------------------------------------
Requirement:
Users need to know exactly when a signal was issued, how many days it has been
on screen, when it was removed, and whether a fixed 5-day rule is realistic when
holidays or regime shifts occur.

Implementation & Architecture:
- Exact Timestamping: Each signal records its microsecond ISO issuance timestamp
  (`issued_at`).
- Live Fractional Duration: In `signals_lifecycle`, the active elapsed time is
  continuously calculated:
  `days_active = Math.round((elapsedMs / (1000 * 60 * 60 * 24)) * 10) / 10`
  Displayed in the desk interface as: e.g., "0.3 Days Active (Day 1 of 5)".
- Dynamic Holding Horizon (Beyond Fixed 5-Day Cutoffs):
  Rather than an inflexible 5-day calendar cutoff that prematurely liquidates
  profitable swings due to NSE public holidays or low-volatility consolidation,
  the engine computes dynamic expected horizons (`horizon_days`) based on:
  1. Average True Range (ATR-14) relative to the distance to Target 1 / Target 2.
  2. Implied Volatility (IV) regime (expansion vs. contraction).
  3. Market session progression and scheduled NSE holiday calendars.
- Explicit Removal Lifecycle: When a signal hits Target (+2.5%), Stop (-1.5%),
  or its dynamic horizon, it transitions from `ACTIVE` to `TARGET_HIT`,
  `STOPPED_OUT`, or `EXPIRED_REMOVED`, recording `closed_at`, `exit_reason`, and
  final PnL.

2.3. FOLLOW-TRADE PROFIT & LOSS TRACKING WITH ZERO-FABRICATION ACCURACY
----------------------------------------------------------------------
Requirement:
If a user follows the trade, there must be exact profit or loss tracking, and
the system accuracy scorecard must reflect real follow-trade results rather than
made-up statistics.

Implementation & Architecture:
- Unit-Level and Rupee-Level PnL: For every signal, the engine tracks:
  `pnl_points = current - entry` (for BUY)
  `pnl_pct = (pnl_points / entry) * 100`
  `pnl_rupees = pnl_points * lot_size`
- Elimination of Seeded Ledger Fraud: The previous code included a seed routine
  (`seedDefaultData()`) that inserted 7 synthetic closed trades to manufacture
  a fake 71.4% win rate and +Rs 51,492.50 profit. This was completely removed.
- Honest Cold-Start Scorecard:
  When the desk has zero closed signals, it outputs:
  ```json
  "accuracy": {
    "winCount": 0,
    "lossCount": 0,
    "totalSignals": 0,
    "winRatePct": null,
    "totalFollowPnl": null,
    "avgDaysOnScreen": null,
    "profitFactor": null,
    "hasTrackRecord": false,
    "archived": []
  }
  ```
  The UI displays an honest banner: "Track record begins accumulating as live
  signals complete their lifecycle." Win rate and PnL are earned solely through
  verified, closed trades.

2.4. STRUCTURAL SEGREGATION: ACTIVE RECOMMENDATIONS VS. PURCHASED TRADES
------------------------------------------------------------------------
Requirement:
Users must not have their purchased positions mixed up with general market
recommendations. There must be a dedicated "Purchased Trades" view.

Implementation & Architecture:
- Two-Tier Interface Architecture:
  1. "Active Recommendations" Tab: Displays incoming quantitative setups,
     screening metrics, neural confidence, and dynamic horizons.
  2. "📦 My Purchased Trades" Tab: A dedicated, segregated private portfolio
     ledger where users track their active investments.
- 1-Tap Broker Execution: On every candidate card, the user can click:
  "💼 I Bought This (Move to Purchased Trades)".
- Isolated Live MTM Monitoring: Once clicked, the trade is stored in the
  local/SQLite portfolio database, tracking mark-to-market PnL, days held, and
  allowing 1-click manual closure via `POST /api/action/close`.

Requirement:
Target the entire Indian market Call and Put universe without missing any

3. REMEDIATION OF PREVIOUS AUDIT FINDINGS (WHAT WAS BROKEN & HOW IT WAS FIXED)
================================================================================

3.1. CRITICAL SECURITY VULNERABILITY: DATABASE EXFILTRATION & PATH TRAVERSAL
----------------------------------------------------------------------------
- Finding: The Node.js static file server used `path.join(__dirname, safePath)`
  without root directory containment. A remote client requesting
  `GET /.private/k2-trading.db` received the raw SQLite database file with
  HTTP 200 OK, exposing all tables, positions, and operational data.
- Remediation:
  1. Pinned static root to `STATIC_ROOT = path.join(__dirname, "site")`.
  2. Implemented strict directory traversal containment:
     `if (!fullPath.startsWith(STATIC_ROOT)) -> 403 Forbidden`.
  3. Added dotfile blocking: any filename or path segment starting with `.`
     returns `404 Not Found`.
  4. Added URIError protection for malformed percent-encoded paths.
  5. Implemented strict 404 routing for unknown `/api/` paths (preventing
     misleading HTTP 200 SPA fallthrough).
- Verification: Probed `https://k-square31.onrender.com/.private/k2-trading.db`
  live; returned `HTTP 404 Not Found`.

3.2. ERADICATION OF FABRICATED PERFORMANCE & SEED DATA
------------------------------------------------------
- Finding: In `api/_lib/db-sqlite.js`, `seedDefaultData()` automatically
  populated `signals_lifecycle` with 7 pre-programmed rows (5 TARGET_HIT, 2
  STOPPED_OUT), presenting an unearned "71.4% Win Rate" and "+₹51,492.50" profit.
- Remediation:
  1. Completely deleted `seedDefaultData()`.
  2. Initialized SQLite databases with empty ledger tables (`winCount: 0`,
     `lossCount: 0`, `winRatePct: null`, `hasTrackRecord: false`).
  3. Built and enforced `scripts/test-no-fabricated-values.js` across the entire
     codebase to fail the build if fabricated figures reappear.

3.3. REPAIR OF 4 MATHEMATICAL CALCULUS DEFECTS
----------------------------------------------
- Finding: Four quantitative formulas contained mathematical defects:
  1. Cornish-Fisher Expansion: Non-monotonic polynomial expansion under extreme
     skewness/kurtosis produced inverted quantiles. Fixed with boundary clamping.
  2. Conditional Value at Risk (CVaR / Expected Shortfall): Tail integration
     clipped probability mass. Corrected to exact Gaussian tail density integral.
  3. GARCH(1,1) Volatility Model: Failed variance targeting condition.
     Restructured to enforce stationary baseline: omega = V_L * (1 - alpha - beta).
  4. Kyle's Lambda (Microstructure Liquidity): Order flow covariance regression
     failed on singular matrices. Added Ridge regularization parameter.
- Verification: Guarded by automated unit tests in `npm run check`.

3.4. ELIMINATION OF SYNTHETIC SINE-WAVE PRICING
-----------------------------------------------
- Finding: 120 of 210 symbols derived spot prices from ASCII character code
  hashes (`spot = 200 + (charCodes % 2800) + ...`) and generated bars from
  `Math.sin(i * 0.4)`.
- Remediation:
  1. Created `api/_lib/bar-cache.js` to fetch and store genuine daily and 15m
     OHLCV historical bars from Yahoo Finance.
  2. Fallback to offline cache with strict provenance flags (`priceSource:
     "NSE_YAHOO_BARS"`).
  3. Rebuilt recommendation and portal templates to display only verified
     candidates.
