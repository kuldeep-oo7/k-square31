  accuracy.

P0-01 -- ONE PRODUCT, FOUR DIFFERENT STRATEGIES
Status: OPEN

WHAT is wrong?
  The historical engine forces all remaining positions out on Friday. The AI
  engine carries cash-style long lots. Recommendations describe stock-futures
  orders with dynamic stops/targets. The alert triage uses a separate hard-coded
  -2.5% rule. These are not the same strategy.

WHERE?
  api/_lib/weekly-cycle.js:1-10, 142-146, 324
  scripts/test-weekly-cycle.js:43-57
  api/_lib/ai-engine.js:135-146, 177-271
  api/_lib/recommendation.js:283, 492
  scripts/dispatch-daily-alert.js:107-143

WHY does it matter?
  The backtest and ML labels estimate a Friday-liquidated cash-bar strategy,
  while the stated trading policy carries futures across weeks. Its expected
  return, drawdown, hit rate, holding time, costs, gap risk, and labels therefore
  do not describe the intended live behavior.

WHO is affected?
  Research, ML, ranking, shadow execution, P&L reporting, risk controls, and the
  trader relying on the recommendation.

WHEN does it fail?
  Every Friday with an open position, every Monday rebase, every contract expiry,
  and every evaluation that uses weekly-cycle output as live evidence.

HOW must it be fixed?
  Define one versioned StrategySpec and one event-driven engine. The same engine
  must consume historical events for research and live events for shadow/live.
  StrategySpec must define instrument, side, entry, fill, stops, targets, sizing,
  daily settlement, Monday attribution, holding exit, roll, costs, and vetoes.
  Remove forced Friday exit from the canonical strategy if continuous holding is
  the user's policy. Do not merely change the description.

ACCEPTANCE TEST
  Given the same deterministic market-event fixture, research and shadow modes
  must produce identical orders, fills, positions, exits, fees, and P&L. Friday
  must create zero exit event unless a real exit rule fires.

P0-05 -- MONDAY REBASE PROOF IS SYNTHETIC, NOT A PRODUCTION TEST
Status: PARTIAL / OPEN

WHAT is real?
  ai-engine has code that retains lots Friday and changes weekly reference Monday.
  shadow-ledger has a rebase helper.

WHAT is not proven?
  scripts/test-weekly-rebase.js imports only assert and defines its own
  simulateWeeklyRebaseEngine. It does not call ai-engine, shadow-ledger, the
  runner, or broker. Its roll event is a manually constructed object. The test
  proves its own example, not production.

WHERE?
  scripts/test-weekly-rebase.js:3-13, 119-139
  api/_lib/ai-engine.js:230-271
  scripts/test-shadow-ops.js (manual helper exercise)

ACCOUNTING GAPS
  - ai-engine is a cash-equity ledger: cash is reduced by full purchase amount and
    only long lots exist. That is not futures margin + daily variation settlement.
  - previousSettlementPrice is updated on Friday, not every session.
  - No daily MTM cash movement or T+1 settlement ledger is modeled.
  - No runtime invariant reconciles daily MTM, weekly attribution, weekend gap,
    fees, and lifetime P&L.
  - If Friday processing is missed, the Monday gap base can be stale.
  - Weekend gap formula is long-only.

CORRECT POLICY
  Monday open may become the new WEEKLY REFERENCE price while the original trade
  price, quantity, side, contract, and lifetime P&L remain unchanged. That reset
  is reporting attribution only; it is never a new buy and never erases economic
  P&L. For futures, daily settlement reference must also be stored separately.

REQUIRED THREE-PRICE MODEL
  1. originalExecutionPrice -- immutable lifetime/trade economics
  2. previousDailySettlementPrice -- daily variation-margin accounting
  3. weeklyReferencePrice -- Monday-to-current reporting attribution

ACCEPTANCE INVARIANT
  lifetime gross P&L == sum(all daily MTM) == sum(prior weekly attribution,
  weekend gaps, current weekly attribution), subject only to explicit rounding.
  A rebase must change no position quantity, side, contract, original execution,
  realized P&L, account equity, or fee balance.

5. P1 HIGH DEFECTS / CALCULATION ERRORS
======================================================================

P1-01 -- IPFT RATE IS 100 TIMES TOO HIGH
  Code comment says INR 0.01 per crore but multiplies turnover by 0.0000001.
  Correct decimal rate for INR 0.01 / INR 10,000,000 is 0.000000001 (1e-9).
  api/_lib/shadow-broker.js:78-79
  scripts/test-shadow-broker.js:19 incorrectly locks in INR 0.08 on INR 750,000;
  correct IPFT at INR 0.01/crore is INR 0.00075 before currency rounding.
  NSE's revised combined equity-futures outflow is INR 182.99 transaction charge
  + INR 0.01 IPFT = INR 183 per crore each side. Code charges 0.00183% (INR 183)
  plus an extra oversized IPFT, so it over/double counts relative to that split.

P1-02 -- COST ENGINE IS FRAGMENTED
  weekly-cycle = 0.08%; upside/tracker = 0.08%; strategy-lab = 0.25%; portal copy
  still says 0.06%; shadow-broker itemizes charges. One trade can have different
  expected net return depending on module. Build one dated, instrument-specific
  charge service and make all research/live paths call it.

P1-03 -- TICK SIZE IS WRONG FOR STOCKS BELOW INR 250
  recommendation.js:98 and bhavcopy.js:112 hard-code 0.05. Current NSE contract
  specification says stock futures use the underlying cash-market tick: INR 0.01
  below INR 250 and INR 0.05 at/above INR 250. Load tick from instrument master.

P1-04 -- MARGIN IS A FLAT ESTIMATE, NOT CURRENT SPAN
  recommendation.js:119-121 uses 22%/28%. NSE Clearing margin is online,
  intraday, portfolio-based SPAN and can include ELM, delivery margin, crystallized
  obligations, additional volatile-stock margin, and broker add-ons. Use broker/
  clearing current margin plus a conservative outage buffer; reject stale data.

P1-05 -- EXPECTED WEEKLY RETURN REMAINS PARTLY INFLATED
  Capital-weighted weekNetPct is improved, but weekly-cycle.js:278 calculates
  expectedWeeklyPct by summing level average return * fills/week without the same
  capital-slot weights. OOS average is for all rungs, not necessarily the selected
  viable set. Expected return, ranking, sizing, and displayed economics must all
  use one portfolio cash-flow calculation.

P1-06 -- DAILY-BAR STANDARD ERRORS OVERSTATE EFFECTIVE SAMPLE SIZE
  Multiple rungs in one week and hundreds of symbols on one date share shocks.
  sqrt(number of rows/fills) assumes independence that does not exist. Use weekly/
  date block bootstrap, clustered uncertainty, and regime/time stability checks.

P1-07 -- VPIN IS NOT VPIN
  advanced-quant builds a daily-bar price/volume proxy with arbitrary thresholds.
  Institutional VPIN requires volume-bucketed order-flow estimation from suitable
  trade data. Rename it clearly as a proxy or implement/calibrate real inputs. A
  hard trade veto must not depend on an unvalidated mislabeled proxy.

P1-08 -- META-LABEL IS HAND-CODED, NOT A VALIDATED META-MODEL
  metaLabelConfidence is a formula with magic coefficients and an absolute veto.
  It has no trained probability calibration, temporal validation, reliability
  plot, Brier/log loss, threshold-cost study, or drift monitor. Rename it to rule
  score until those proofs exist.

P1-09 -- BLACK-76 PRICE FIX IS PARTIAL
  Futures-option price/delta use discounting, but gamma and vega omit the discount
  factor and theta/rho still follow spot-style expressions. This module is outside
  the pure stock-futures core; either correct it with numerical finite-difference
  tests or remove it from production claims/scope.

P1-10 -- ACTIONABILITY DOES NOT REQUIRE EXECUTABILITY
  rankRecommendations filters action != stand-aside but not executable intents.
  Missing/invalid contract rows can be counted as actionable. Actionable must mean
  every required rung is schema-valid, current, risk-approved, and executable.

P1-11 -- BHAVCOPY FAILURE BROADENS THE UNIVERSE
  weekly-plan.js:105-114 returns an empty futures map and then scans stored names.
  For a pure stock-futures product, failure to prove current F&O eligibility must
  produce NO TRADE, not a larger cash-equity universe.

P1-12 -- NO LIQUIDITY/CAPACITY/F&O-BAN GATE

  freeze, MWPL, ban status, contract days-to-expiry, or participation rate. These

P1-13 -- CONTRACT SYMBOL IS SYNTHETIC
  recommendation.js:107-108 constructs SYMBOL-expiry-FUT. Broker/exchange

  versioned. A display string cannot serve as execution identity.

P1-14 -- SHORT HOLDING P&L IS WRONG IN ALERT TRIAGE

P1-15 -- TEST HARNESS CAN PASS CLAIMS WITHOUT TESTING THE REAL PATH

P1-16 -- DEPENDENCY AUDIT IS NOT A RELEASE GATE

8. REQUIRED HOLDING AND MONDAY-RESET DESIGN
======================================================================

The user's policy is valid as an attribution choice:
  - Do not automatically close Friday.
  - Carry the actual position over the weekend.
  - Use the first tradable Monday/new-week open as weeklyReferencePrice.
  - Reset weekly displayed P&L only.
  - Preserve original entry and total/lifetime P&L.
  - Record Friday-to-Monday gap separately.

It is not valid to call Monday open a new buying price for economic/accounting
purposes unless there is a real new fill. Better terminology is NEW WEEKLY
REFERENCE PRICE. Calling it "buy price" risks tax, ledger, stop, and performance
errors.

Holding horizon recommendation:
  Do not hard-code one week. Start with a conservative maximum defined relative to
  expiry and validated time-to-edge decay. Until there is valid futures history,
  the system must not pretend it knows the optimal number. Research candidates
  such as 5/10/15/20 sessions plus target/stop/trailing/thesis exits using nested
  walk-forward testing. Always force genuine close/roll before the operational
  expiry/physical-settlement danger window. The selected rule must be frozen and
  prospectively shadow-tested for at least one or preferably two full expiry
  cycles before any limited-capital proposal.

12. WHAT WOULD MAKE THE SYSTEM BETTER (AND WHAT WOULD NOT)
======================================================================

High-value improvements after the P0 foundation:
  - Point-in-time actual futures data and contract lifecycle.
  - Market/sector-neutral residual features and explicit beta/exposure controls.
  - Volatility/liquidity normalized entries, but only after walk-forward ablation.
  - Distributional forecasts and calibrated probabilities, not one point target.
  - Tail metrics: max drawdown, expected shortfall, worst gap, time under water,
    margin stress, turnover/capacity, and probability of ruin.
  - Regime-specific champion/challenger models with evidence-based gates.
  - Survival/hazard analysis for time-to-target/stop to estimate holding horizon.
  - Execution-cost model calibrated from shadow/live fills.
  - Independent model validation and continuous outcome/drift monitoring.

Likely downgrades if added without proof:
  - More chart patterns, candlesticks, physics metaphors, deep networks, or exotic
    equations on only five years of daily data.
  - Treating every technical indicator as independent confirmation.
  - Using LSTM/transformers/deep learning before data volume, timing, labels, and
    costs are correct.
  - Optimizing rules on the same OOS period shown as proof.
  - Auto-promoting a model because it sounds institutional or was recommended by
    another model.

Promotion rule for every new feature:
  It must have a written causal/economic hypothesis, correct as-of data, ablation,
  nested walk-forward test, untouched final test, conservative costs/fills,
  stability across regimes, capacity assessment, and documented failure modes.
  If it cannot improve net utility with uncertainty, keep it out.
