P0-001: META VETO IS BYPASSED BY THE POTENTIAL ROUTE
----------------------------------------------------
Status:
  CONFIRMED CODE DEFECT AND REPRODUCED.

Where:
  api/_lib/recommendation.js
  function potentialCall(), lines approximately 90-180
  meta gate calculated around lines 121-133
  trade returned around lines 135-179

Correct comparison path:
  same file, normal ladder route, lines approximately 328-333

What is wrong:
  potentialCall calculates metaLabelConfidence and records metaDecision, but it
  never returns stand-aside when metaDecision is VETO. It clamps sizing to a
  positive minimum.

Observed reproduction:
  action: buy-potential
  metaDecision: VETO
  metaProb: approximately 0.383
  vpin: approximately 0.866
  sizeMultiplier: non-zero

Why it matters:
  A stated hard risk control is only applied to one route. A new or fallback
  route can trade precisely when the safety model rejects the trade.

Required resolution:
  Create one shared enforceHardVetoes() function and invoke it after all evidence
  is assembled but before any actionable object is returned. No route may create
  a positive size when a hard veto exists.

Acceptance tests:
  1. Potential long plus meta VETO => stand-aside and size 0.
  2. Potential short plus meta VETO => stand-aside and size 0.
  3. Ladder long/short behave identically.
  4. Missing/invalid meta evidence follows the declared fail-closed policy.
  5. Property test: every actionable recommendation has no hard veto and size > 0;
     every hard-veto result has action stand-aside and size 0.

4. P2 MATERIAL FEATURES/IMPROVEMENTS NEEDED FOR THE REQUESTED SYSTEM

P2-001: INSTITUTIONAL DATA PLANE
--------------------------------
Implement:
  - licensed NSE F&O real-time/1-minute/tick data or authorized vendor;
  - exact historical contracts, quotes, trades, OI and contract master;
  - immutable raw zone with hashes and source timestamps;
  - normalized point-in-time feature zone;
  - quality rules, missingness, corrections, late data and lineage;
  - corporate actions, dividends, symbol and lot changes;
  - historical eligible-universe snapshots.


P2-002: FULL POINT-IN-TIME FUNDAMENTALS/EVENT PLANE
---------------------------------------------------
Implement:
  - NSE XBRL financial results and filing timestamps;
  - full P&L, balance sheet, cash flow and notes;
  - consolidated/standalone and period taxonomy;
  - original/revised/restated versions;
  - results dates and actual announcement timestamps;
  - board actions, dividends, splits, mergers, pledges, shareholding;
  - ratings, defaults, restructuring, auditor qualifications;
  - sector-specific ratios for industrials, banks, NBFCs, insurers, REITs.

Use fundamentals primarily as event/risk and regime features for weekly futures.
Do not assume P/E or any single ratio has universal short-horizon alpha.


P2-003: SHARED EVENT-DRIVEN RESEARCH/LIVE ENGINE
------------------------------------------------
One state machine must power:
  backtest
  paper
  shadow
  live
  outcome audit

It must model:
  exchange calendar/time zone
  data events
  order submission/acknowledgment
  fill/partial fill/rejection
  stops/targets/time exits
  fees/slippage/impact
  positions/cash/margin
  rolls/expiry/settlement
  recovery/restart/reconciliation

NautilusTrader and LEAN are useful reference engines, but neither creates alpha,
and India futures require licensed/custom data integration.

----------------------------------------------
Implement independent:
  risk budget
  volatility target
  name/sector/factor/correlation caps
  liquidity/capacity
  margin buffer
  daily/weekly loss limit
  drawdown stages
  gap/limit stress
  broker/order kill switch
  stale-data kill switch
  operator emergency stop

  hypothesis
  data version
  feature/label version
  parameters/trials
  train/validation/test periods
  costs
  result
  owner
  decision

Predict:
  probability of fill

  expected net P&L
  expected shortfall
  prediction interval

Measure:
  Brier score
  calibration/reliability
  coverage
  precision by confidence band
  stability/drift

Allow the model to abstain. A high-quality system should often say no trade.


P2-007: TECHNICAL/CANDLE/PATTERN LIBRARY WITH EMPIRICAL GATING
--------------------------------------------------------------
It is reasonable to add more candlestick and chart definitions only if:
  - definitions are deterministic;
  - feature availability/confirmation time is explicit;
  - context such as trend, volatility, volume and liquidity is included;
  - overlapping labels are handled;
  - all tried patterns enter multiple-test correction;
  - only incremental OOS net value affects production.

"All candlesticks" is not a quality goal. A smaller validated set is better than

8. VALIDATION STANDARD: WHAT "TIME-TESTED" MUST MEAN
======================================================================

A METHOD IS NOT VALIDATED BECAUSE:
  - a bank or hedge fund has used a technique;
  - a paper reported an effect in another market/period;
  - its name includes AI, physics, VPIN, Kelly, Black-Scholes, Hurst, or quant;
  - code exists;
  - unit tests pass;
  - an in-sample backtest is profitable;
  - a document declares it fixed.

THE INTEGRATED SYSTEM IS VALIDATED ONLY WHEN:
  1. Data is legally obtained, immutable, point-in-time and reproducible.
  2. The historical universe has no future membership/survivorship leakage.
  3. Labels exactly match the executable strategy.
  4. Research and live share execution semantics.
  5. Costs, liquidity, margin, rolls and settlement are modeled.
  6. Every experiment/trial is recorded.
  7. Split boundaries are purged/embargoed.
  8. A final holdout is untouched until design is frozen.
  9. Multiple testing/backtest overfitting is measured.
 10. Results are stable across dates, regimes, sectors and cost stresses.
 11. Probabilities are calibrated and uncertainty/abstention are reported.
 12. Portfolio drawdown/tail/capacity and operational failures are acceptable.
 13. Shadow fills/fees/positions/P&L reconcile with real observable outcomes.
 14. Independent review challenges assumptions and signs off limitations.
 15. Ongoing monitoring can automatically disable a degraded system.
